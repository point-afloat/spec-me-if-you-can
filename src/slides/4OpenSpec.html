OpenSpec

One implementation of the idea (https://github.com/Fission-AI/openspec). Others exist. Commands shown are the OpenSpec 1.x /opsx:* commands (explore, propose, apply, update, sync, archive). In OpenSpec 2.0 they became skills (/openspec-propose, /openspec-apply-change, ...): check which ones the demo repo uses before the talk. /opsx:verify is in the expanded profile only.

A spec says what the software
should do, not how.

General definition: a precise description of what a system must do, independent of the implementation, written so that one party can build it and another can check it. Contracts, API specs and standards work this way. The how is the code (in OpenSpec also design.md). Böckeler distinguishes spec-first, spec-anchored and spec-as-source; by her definitions OpenSpec fits spec-anchored (my reading: her article covers Kiro, spec-kit and Tessl, not OpenSpec): https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html Q&A, if asked whether every task needs a spec: no. Throwaway scripts and exploration do not. Match the ceremony to the stakes, and prototype first when you don't know yet what you want.

Written down. Checkable. Kept.

The three properties answer the three problems from the vibe-coding chapter: intent only in the chat -> written down, in the repo; nothing to check against -> checkable: scenarios become tests; nothing protects what works -> kept: living specs plus tests protect existing behavior.
Explore think it through
Propose writes it down
Apply builds and checks it
Archive keeps it
The loop is enough, no command list. Verify is optional. One intent per change, explore before proposing. Maps the three properties to the loop: Propose creates the change with the spec deltas (written down). Apply builds against it, with tests as the check (checkable). Archive merges the deltas (ADDED / MODIFIED / REMOVED Requirements) into the living specs in openspec/specs/ (kept). That merge separates OpenSpec from "write a doc first".

## ADDED Requirements

### Requirement: Ranked standings
The system SHALL rank players by marked words,
highest first.

#### Scenario: Higher score ranks first
- **GIVEN** A has 5 marked words and B has 3
- **WHEN** the standings are shown
- **THEN** A is ranked above B

#### Scenario: Pizza does not count
- **WHEN** only the pizza center is marked
- **THEN** the score is 0
Here is one. Shortened from the real leaderboard-v2 spec of the bingo. A delta header, one requirement with one SHALL, scenarios in GIVEN / WHEN / THEN, and an edge case, not only the happy path. Behavior goes in the spec, the how goes in design.md. The real files are shown live in the demo.
